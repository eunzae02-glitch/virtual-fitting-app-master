# S/M/L 합성 결과의 길이·폭이 같아 보이는 문제

작성: 2026-10-25. 로컬 HEAD `cc60714`와 현재 작업 파일 기준.
최초 요청 범위: 원인 조사와 디버깅 절차 기록. 당시 앱·모델·UI 코드는 수정하지 않았다.
이후 같은 날 사용자의 수정 요청으로 아래 보완을 반영했다. 1~5절은 수정 전 조사 기록이며,
당시 줄 번호·출력 해시·테스트 결과는 수정 전 코드 기준이다.

## 0. 후속 수정 — FASHN 경로 우선, DM-VTON 보류

**복원 최신 변경**: 기본 복원은 `reference_directional_patch_v2`다. 아래 Telea 보완은 이전 실험
기록이며 `legacy_telea_plate()`에 보존한다. 이번에는 기준점·총장·가슴·어깨 변형식은 바꾸지 않았다.

- `scripts/debug_size_preview.py`의 목표선 계산 이벤트에 후처리를 순서대로 연결했다.
  마스크 확인 체크를 켜면 적용하며, S/M/L을 바꿀 때도 새 목표선으로 자동 재적용한다.
  선택 이벤트에 따로 붙었던 결과 초기화와 적용 응답의 경쟁을 제거했다.
- `app/size_synthesis.py`의 `adjust_sizes()`가 공통 기본 합성과 확인 마스크를 재사용해
  전체 판매 사이즈를 계산한다. 결과는 갤러리로 비교하고 기본 합성은 접힌 영역에 구분한다.
  선택 사이즈·목표 좌표·실제 변경 화소·조정 RGB/목표 마스크 해시를 기록한다.
- 축소 시 `repair` 부분만 복원하던 방식을 바꿨다. 복원용 영상에서는 기존 옷 전체와 경계 1px를
  제외하고 Telea를 실행한 뒤, 필요한 `repair` 영역만 가져온다. 나머지 비편집 화소는 보존한다.
  변형 버전은 `masked_torso_warp_v1`, 복원 방식은 `garment_excluded_telea_v1`이다.
  아래 D의 통제 사례에서 목표 마스크 밖 빨간 옷 픽셀이 **708개 → 0개**로 줄었다.
  이는 복원 정답이나 실제 착용 핏을 확보했다는 뜻은 아니다.
- 기본 합성 중에는 관련 입력을 잠가 오래 걸리는 생성의 입력·결과가 엇갈리지 않게 한다.
  생성 실패 시 조정 결과를 비우고 입력을 다시 연다.
- `notebooks/debug_size_fashn.ipynb`로 FASHN 설치·가중치 준비와 **사이즈 화면**을 연결했다.
  기본 합성만 보여주는 `debug_synthesis.ipynb`와 구분한다. 서버는 새 프로세스에서 실행해
  기존 import 캐시의 코드가 남지 않도록 하고, 포트는 자동 선택한다.
- `00_ME` 사진은 필수가 아니다. 자료가 없는 환경에서는 예시 버튼을 숨긴다.
  사진 왕복 테스트는 인공 사진으로 실행하고 실제 00_ME 테스트만 자료가 없으면 명시적으로 건너뛴다.

현재 확인 순서는 **치수·5점·측정 기준 확인 → FASHN 기본 합성 한 번 → 옷 마스크 확인 체크 →
전체 사이즈 갤러리 / 선택 사이즈 자동 갱신**이다. 이미 생성한 기본 합성 PNG도 사용할 수 있다.
저장한 `synthesis.json`의 `size_comparison.rows`에는 전체 사이즈의 목표 좌표·출력 해시가 있으며,
`adjusted.png`는 현재 선택 사이즈다. 일부 사이즈가 사진 밖으로 나가면 해당 사이즈만 보류한다.

FASHN 가중치 준비는 [공식 다운로드 스크립트](https://github.com/fashn-AI/fashn-vton-1.5/blob/main/scripts/download_weights.py)를 사용한다.
이 스크립트가 합성·포즈 가중치와 Human Parser 캐시를 준비하므로 준비 셀 완료 후 오프라인 기본 합성을 실행한다.
이 PC에서는 CPU 후처리와 모의 생성으로 연결을 검증하며, 실제 CUDA 합성과 복원 품질은 Colab에서 확인해야 한다.

후속 검증 결과:

- 합성·후처리·자동 UI 연결 테스트 17개 통과, 목표선 테스트 9개 통과·개인 사진 테스트 1개 건너뜀,
  기존 기본 합성 화면 테스트 3개 통과. 총 29개 통과·1개 건너뜀.
- 실제 Chrome 브라우저에서 인공 사진과 모의 FASHN 엔진으로 **기본 생성 1회 → 마스크 확인 →
  S/M/L 선택**을 실행했다. 결과 이미지 URL은 세 개가 서로 달랐고 브라우저 오류·실패 HTTP 요청은 없었다.
- 이 검증에서 발견한 Gradio 입력 해제 문제(`interactive=None` 복원), ImageEditor canvas 재생성 문제,
  Windows의 레이어 업로드/읽기 충돌도 보완했다. 편집기 자체의 interactive를 스트리밍 중 바꾸지 않고,
  확인된 일시적 파일 잠금은 최대 150ms만 기다리며 계속 잠겨 있으면 업로드 보류 오류를 낸다.
- 선택적 브라우저 재현: `python -X utf8 tests/browser_size_synthesis_smoke.py`.
  Playwright와 설치된 Chrome/Edge 또는 `PLAYWRIGHT_CHROMIUM_EXECUTABLE`이 필요하다.
  GPU나 실제 사진은 사용하지 않는다. 원래 FASHN 확산 모델의 CUDA 생성 품질은 이 시험에 포함되지 않는다.

### 후속 수정 — 같은 사진인데 옷 영역의 사진이 바뀌었다고 보류됨

브라우저에서 초안 위를 수정하면 `옷 영역 편집기의 사진이 바뀌었습니다`가 발생하는 것을 재현했다.
기존 편집기에 원본·투명 마스크 외에 **초록색을 합친 composite**까지 전달했는데, 수정 후 그
composite가 배경으로 반환돼 원본 해시와 달라졌다. 인공 사진의 차이 화소는 초안 면적과 같은
12,231개였다. 사진 크기·색상이 복잡해서 생긴 해시 오차가 아니므로 허용 오차로 우회하지 않았다.

composite 전달을 없앤 뒤에도 현재 Gradio 6.30.0 ImageEditor의 초기 레이어가 화면에서 벗어나거나
수정 후 비는 현상을 확인했다. 따라서 4단계의 **마스크 편집 부분만**
`scripts/garment_mask_editor.py`의 원본 고정 이미지와 투명 2D 캔버스로 교체했다.
브러시·지우개·크기·초안 복원만 제공한다. 배경 PNG는 처음 받은 그대로 전송하고,
투명 마스크만 바꾸므로 지우개로 초기 초안을 지워도 사진 화소는 바뀌지 않는다.
기존 해시·사진 연결·크기·확인 상태 검사는 유지했다. 기존 ImageEditor 전용 캐시 읽기와
파일 잠금 재시도는 이 화면에서 더 이상 사용하지 않는다.

Chrome에서 **기본 합성 → 확인 → 지우개 → 재확인 → 브러시 → 재확인 → S/M/L 변경**을 실행했다.
옷 마스크 면적은 12,231 → 11,813 → 12,231px로 변했고, 수정할 때마다 확인이 해제됐다.
다시 지운 뒤 `초안으로 되돌리기`를 눌러 최초 마스크와 완전히 같은 결과로 복원되는 것도 확인했다.
재확인 후 세 사이즈의 조정 이미지가 서로 달랐고 모의 FASHN 생성은 1회였다.
브라우저 오류와 실패 HTTP 요청은 없었다. 실제 CUDA 합성과 실착 품질 검증은 포함하지 않는다.
관련 합성·목표선·기본 합성 화면 테스트는 총 30개 통과, 개인 사진이 필요한 1개만 건너뛰었다.

적용 방법: PC에서 Commit·Push → 실행 중인 Colab 서버 셀 중지 → 최신 사이즈 노트북의
2번(코드)·3번(설치)·5번(서버) 셀 재실행. 3번은 검증한 Gradio 6.30.0을 설치한다.
이미 준비한 가중치를 다시 다운로드할 필요는 없고, 저장한 기본 합성 PNG도 재사용할 수 있다.
새 화면의 `브러시 / 지우개 / 크기 / 초안으로 되돌리기`가 보이면 수정본이다.

### Colab 3번 셀 설치 충돌 수정

사용자 Python 3.13.16의 pip 로그에서 `ResolutionImpossible`을 확인했다.
Gradio 6.30.0은 `huggingface-hub>=1.16,<3`을 요구하지만, 기존 셀의
`transformers>=4.40,<5`는 `huggingface-hub<1.0`을 요구해 동시에 설치할 수 없었다.
Gradio 미배포나 CUDA 합성 오류가 아니라 설치 셀의 서로 모순되는 의존성 제한이었다.

사이즈 화면에서 확인한 Gradio를 유지하고, 해당 노트북 3번 셀의 Transformers를
`5.20.2`로, Hub 범위를 `>=1.31,<3`으로 수정했다.
[Transformers 5.20.2 배포 메타데이터](https://pypi.org/pypi/transformers/5.20.2/json)의 Hub 요구 범위와
Gradio 요구 범위가 겹침을 확인했다. FASHN Human Parser가 사용하는
`SegformerForSemanticSegmentation`은 해당 버전의 공식 소스에서 확인했다.
pip 출력은 명시적으로 캡처해 표시하고, 설치 뒤 별도 프로세스에서 SegFormer·Human Parser·FASHN의
import를 확인한다. import 실패 시에는 4·5번 셀로 넘어가지 않는다.
로컬에서는 셀 구문·명령 구성·실패 출력 보존을 모의 실행으로 검증했다.
새 조합의 실제 Colab 설치·캐시된 가중치 로딩·CUDA 합성은 사용자의 런타임에서 확인해야 한다.
다른 과거 엔진의 의존성까지 일괄 변경하거나 `--no-deps`로 충돌을 무시하지 않는다.

### 밑단 아래 삼각형 번짐 후속 — 복원만 수정

`app/garment_repair.py`가 기존 옷 전체를 지운 Telea 결과 대신 아래 순서로 `repair` 영역만 채운다.

1. 원본 옷 제외 초안과 확인한 밑단보다 충분히 아래인 몸통 범위에서 원본 재사용 후보를 찾는다.
   가까운 가시 영역의 RGB 일치 조건을 통과해야 복사한다. 원본 옷 초안이 없거나 비교할 부분이
   부족하거나 색이 다르면 원본 재사용을 보류한다. 곡선 밑단의 옷 초안도 제외한다.
2. 밑단의 미확인 영역은 아래쪽, 옆 틈은 해당 바깥 방향의 옷 아닌 패치를 반사 연장한다.
   옆 피부·배경을 밑단 중앙으로 끌어오는 삼각형 번짐을 피하기 위한 CPU 가설이다.
   가려진 배/허리선을 알아내거나 실제 바지 모양을 생성하는 모델이 아니다.
3. 원본 재사용(초록)·패치 추정(주황) 진단 이미지를 표시하고 각각의 마스크·화소 수를 저장한다.
   목표 옷 마스크와 변형식은 유지하며, 옷/복원 영역 밖의 기본 합성 화소는 보존한다.

`tests/test_garment_repair.py`의 일정한 세로 줄무늬 바지 통제 사례(3,240px)에서
복원 RGB MAE는 이전 56.29, 새 방식 0.00이다. 실제 사진 검증 결과가 아니며 일반화하지 않는다.
원본에서 관측되지 않거나 원본을 재사용할 수 없는 곳은 계속 추정으로 기록한다.
추가 모델·가중치·의존성 설치는 없으므로 Commit·Push 후 Colab 서버를 중지하고
2번(코드 받기)·5번(서버 실행)을 다시 실행한다. 이미 만든 기본 합성 PNG를 재사용할 수 있다.

## 1. 조사 결론

**가장 먼저 확인할 원인은 목표선과 기본 합성의 연결 방식이다. 기존 FASHN 호출에는
S/M/L 치수나 목표 윤곽이 전달되지 않는다. 사이즈는 기본 합성 이후 별도 후처리에서 반영된다.**

기존 화면은 사이즈를 바꾸면 목표선을 다시 계산하지만, 기본 합성 이미지는 유지하고
이전 사이즈 조정 결과는 지운다. `선택 사이즈 적용`을 다시 실행해야 조정 이미지가 나온다.
따라서 상단의 `기본 합성 결과`를 비교하거나 `FASHN 기본 합성 생성`만 반복했다면,
S/M/L을 바꿔도 길이·폭이 바뀌도록 요청한 것이 아니다. 화면이 이 차이를 쉽게 오해하게 만든다.

반면 **후처리 함수와 실제 UI의 적용 콜백을 CPU에서 직접 호출했을 때는 S/M/L별
목표 마스크와 출력 이미지가 달라졌다.** 후처리 자체가 항상 같은 이미지를 반환한다는 현상은
이번 통제 실험에서 재현되지 않았다.

추가로 축소 후 복원에서 옷 색이 목표 영역 밖으로 번져, 마스크보다 옷이 길어 보이는 현상은
단순 테스트 이미지에서 재현했다. 이는 위의 실행 경로 문제와 별도로 확인할 품질 문제다.

당시 Colab의 실행 파일·버전·버튼 실행 기록과 S/M/L 결과 원본은 확보하지 못했다.
현재 로컬 `outputs/`에는 `.gitkeep`만 있다. 아래에서는 코드로 확인한 사실과
당시 사용자 실행에 대한 가능성을 구분한다. GPU 합성을 새로 실행하거나 가중치를 다운로드하지 않았다.

## 2. 코드에서 확인한 경로

```text
기준 옷·S/M/L 치수 → FitPlan → 사이즈별 목표선 ─────────┐
                                                     ↓
인물 사진·상품 사진 → FASHN → 공통 기본 합성 → 옷 마스크 확인
                                                     ↓
                                         선택 사이즈 적용(adjust_size)
                                                     ↓
                                         사이즈 조정 결과(adjusted.png)
```

목표선은 FASHN 입력으로 들어가지 않는다. 같은 사진·설정으로 기본 합성을 재사용하는 것은
정상이며, 달라져야 하는 결과는 후처리 출력이다. 같은 시드라고 실제 GPU 출력의 비트 단위
동일성까지 보장하는 것은 아니지만, 사이즈를 바꿔도 엔진 입력에 치수 변화가 없다는 점은 확실하다.

## 3. 통제 실험 결과

### A. 기본 합성에는 사이즈가 전달되지 않음

기존 화면의 `make_base` 콜백에 S/M/L preview를 각각 넣고, GPU 엔진만 같은 이미지를 반환하는
모의 엔진으로 대체했다. 호출 인자는 세 경우 모두 다음 항목뿐이었다.

```text
person, garment,
cloth_type, garment_photo_type, guidance_scale, return_timing, seed, steps
```

사이즈나 목표 좌표는 없었다. 반환된 기본 사진의 RGB 해시 앞 12자리는 모두
`6a65339f921f`였고, 조정 이미지 출력은 모두 `None`이었다.
이는 연결 구조를 확인한 실험이며 실제 FASHN을 세 번 생성한 결과가 아니다.

### B. 적용 콜백은 S/M/L별로 다른 결과를 만듦

기존 `tests/test_size_synthesis.py`의 300×400 인공 이미지·마스크·5점을 사용했다.
기준 옷은 총장 65cm, 어깨 51cm, 가슴단면 52cm다.
기준 사진의 목 보조점 y=40, 밑단 y=220, 몸통 좌우 간격=100px로 설정했다.
공통 기본 합성에 `apply_now` 콜백을 실행한 결과다.

| 사이즈 | 입력 총장/가슴단면(cm) | 목표 밑단 y(px) | 변형 마스크 밑단 y(px) | 몸통 기준 높이에서 마스크 좌우 간격(px) | 조정 RGB 해시 앞 12자리 |
|---|---|---:|---:|---:|---|
| S | 55 / 46 | 192.308 | 192 | 88 | `ed0ff1390a2e` |
| M | 65 / 52 | 220.000 | 220 | 100 | `2d3c02842b6b` |
| L | 75 / 58 | 247.692 | 247 | 112 | `170c19880af9` |

여기서 y는 이미지 위쪽이 0인 절대 좌표다. `synthesis.json`의 `target_geometry_px`는
목 보조점을 원점으로 한 로컬 좌표이므로 그대로 숫자를 대조하면 안 된다.
폭은 픽셀 개수가 아닌 오른쪽 x−왼쪽 x다. 정수 격자에 따른 약 1px 차이는 가능하다.
세 출력은 실제 RGB 픽셀도 서로 달랐다. 이는 실제 착용 핏 정확도의 검증은 아니다.

### C. 기존 가상 표의 작은 치수 차이는 눈에 잘 안 보일 수 있음

`sample_values()`의 S/M/L은 총장 63/65/67cm, 가슴단면 50/52/54cm다.
같은 통제 이미지에서 다음과 같이 나왔다.

| 사이즈 | 목표 밑단 y(px) | 마스크 밑단 y(px) | 몸통 기준 높이의 마스크 좌우 간격(px) |
|---|---:|---:|---:|
| S | 214.462 | 214 | 96 |
| M | 220.000 | 220 | 100 |
| L | 225.538 | 225 | 104 |

이 예시에서 S→M 차이는 밑단 약 6px, 전체 폭 4px다. 전신을 작은 화면에 맞추면 더 작게 보인다.
따라서 눈으로 비슷해 보이는 것과 출력 픽셀이 동일한 것은 분리해 확인해야 한다.

### D. 마스크는 짧아져도 옷 색이 남는 복원 문제

B의 S 축소 사례에서 변형 마스크 밑단은 y=192였다. 그런데 조정 이미지의 빨간 옷 색은
y=202까지 남았다. `R > 160, G < 90, B < 90`으로 검사했을 때 목표 마스크 밖의 빨간 픽셀은
708개였으며 y=193~202에 있었다. 원래 옷에서 비워져 복원된 영역은 1,458px였다.

이 영역은 `source_mask & ~warped_mask`를 Telea로 채우는 경로에 해당한다.
**목표 마스크가 변했다는 것만으로 눈에 보이는 옷 실루엣까지 목표선과 같아졌다고 볼 수 없다.**
실제 사진에서 문제를 일으켰는지는 당시 `adjusted.png`와 마스크를 대조해야 한다.
새 DM-VTON 후처리에도 같은 종류의 Telea 복원이 있어 이 품질 검사는 계속 필요하다.

### E. 기존 테스트 결과와 한계

  오류는 `비교할 사진과 TXT 항목이 최소 두 개 필요합니다.`였다. 사진을 복원하거나 테스트를 변경하지 않았다.

## 4. 다음 디버깅 순서 — 합성을 매번 다시 기다릴 필요 없음

### 1단계: 당시 실행 경로부터 확인

Colab 마지막 실행 셀에서 어떤 파일/`build_ui()`를 실행했는지 기록한다.
`app/gradio_app.py`나 `debug_synthesis.py`였다면 기본 합성에 사이즈 변화가 없는 이유가 설명된다.
포트 번호나 GitHub 주소만으로는 어떤 화면·코드가 실행됐는지 알 수 없다.
실제 작업 디렉터리에서 아래를 확인한다. 기존 런타임에 이미 import된 모듈은 git pull만으로
갱신되지 않을 수 있으므로 실행 중인 서버의 버전도 확인해야 한다.

```text
git rev-parse --short HEAD
git status --short
```

### 2단계: 한 장의 기본 합성을 고정

기존 7867 화면에서 이미 만든 기본 합성 PNG를 업로드해 사용한다.
GPU가 없어도 `GPU 없이 기준 사진으로 변형 시험`으로 치수 전달·마스크 변형을 점검할 수 있다.
후자는 새 옷을 생성한 결과가 아니라 기존 사진 변형 시험이라는 점을 기록한다.
인물 사진·기본 합성·마스크는 S/M/L 비교 동안 동일하게 유지한다.

### 3단계: 작은 차이보다 큰 차이로 연결을 먼저 검증

디버깅에 한해 기준 65/51/52cm에 다음 가상 표를 사용한다. 실제 상품 치수나 추천 기준이 아니다.

| 사이즈 | 총장(cm) | 어깨(cm) | 가슴단면(cm) |
|---|---:|---:|---:|
| S | 55 | 49 | 46 |
| M | 65 | 51 | 52 |
| L | 75 | 53 | 58 |

큰 변형이 사진 밖으로 나가면 여백이 있는 사진 또는 더 작은 차이를 사용한다. 보류를 성공으로 취급하지 않는다.
사진–기준 옷 일치와 5점 확인을 마치고, 총장·가슴단면 호환 확인을 모두 켠다.
한 부위만 확인했다면 다른 부위는 의도적으로 유지된다. 두 부위 모두 미확인이면 이 화면은
정상 목표선 생성을 거부하므로, 이를 정상 적용된 동일 이미지와 혼동하지 않는다.
어깨는 현재 변형하지 않으므로 어깨 수치만 바꾸는 실험으로 몸통 변형을 판단하지 않는다.

### 4단계: S/M/L마다 후처리를 실행하고 조정 결과를 저장

각 사이즈에서 목표선의 `선택 사이즈`와 적용 비율이 갱신된 것을 확인한 뒤,
옷 마스크 확인 → `선택 사이즈 적용` → `사이즈 조정 결과`를 본다.
사이즈를 바꾼 직후에는 목표선 갱신이 끝난 뒤 적용한다.
상단 `기본 합성 결과`가 유지되는 것은 정상이다.

각 사이즈마다 `현재 합성·사이즈 조정 실험 저장`을 눌러 다음 파일을 보관한다.
저장 버튼 자체도 현재 입력으로 후처리를 다시 계산한다.

- `synthesis.json`: `preview.fit_plan.selected_size`, `ratios`, `preview.applied`,
  `preview.target_points_px`, `source_geometry_px`, `target_geometry_px`,
  `base.base_sha256`, `mask_sha256`, `preview_sha256`.
- `base.png`: 공통 기본 합성.
- `adjusted.png`: 비교해야 할 사이즈 조정 출력.
- `source_mask.png`, `target_mask.png`, `repair_mask.png`, `adjusted_overlay.png`.

S/M/L별 저장 폴더는 달라야 한다. 같은 기본 사진·마스크를 사용했다면 `base_sha256`와
`mask_sha256`는 같아야 하고, 다른 치수가 실제 적용됐다면 목표 좌표·preview 해시와 조정 출력은
달라지는지 확인한다. `edited_pixels`는 편집 가능 영역의 면적이지 실제 RGB 변경 픽셀 수가 아니다.

### 5단계: JSON → 마스크 → RGB 순서로 비교

| 발견한 상태 | 우선 조사할 곳 |
|---|---|
| 선택은 S/M인데 JSON의 `selected_size`가 같음 | 선택 이벤트, 이전 preview 사용, 실행 중인 코드 버전 |
| 선택은 다르지만 적용된 부위의 비율·목표 좌표가 같음 | 표 입력값, 실제 선택 행, 호환 확인 상태 |
| 목표 좌표는 다른데 변형 마스크가 같음 | `adjust_size` 입력 preview, 원본 마스크, 정수 픽셀 변화량 |
| 마스크와 RGB가 다른데 눈으로 비슷함 | 작은 변화량, 축소 표시, 어깨·소매 고정, 복원 영역 잔상 |
| 다른 조정 PNG가 저장됐지만 UI만 같거나 비어 있음 | 실제 보고 있는 출력 칸, Gradio 상태 초기화/응답 순서 |
| 기본 사진만 있고 조정 결과가 없음 | 후처리 버튼 실행 여부, 마스크 확인/보류 메시지, 다른 UI 진입 여부 |

두 이미지의 해상도가 같다는 것은 정상이다. 비교할 것은 이미지 전체 크기가 아니라 옷의 밑단과
몸통 폭이다. 파일 압축 방식에 영향받는 파일 해시보다 디코딩한 RGB 배열을 비교한다.
다음 코드는 파일을 수정하지 않으며, 경로 두 개를 실제 S/M 저장 폴더로 바꿔 실행한다.

```python
from pathlib import Path
import json
import numpy as np
from PIL import Image

runs = [Path("outputs/size_synthesis/S_실행폴더"),
        Path("outputs/size_synthesis/M_실행폴더")]
rgb, masks = [], []
for run in runs:
    data = json.loads((run / "synthesis.json").read_text(encoding="utf-8"))
    preview = data["preview"]
    print(run.name, preview["fit_plan"]["selected_size"])
    print("ratios:", preview["fit_plan"]["ratios"], "applied:", preview["applied"])
    print("target:", data["target_geometry_px"])
    print("base:", data["base"]["base_sha256"], "source mask:", data["mask_sha256"])
    with Image.open(run / "adjusted.png") as image:
        rgb.append(np.array(image.convert("RGB")))
    with Image.open(run / "target_mask.png") as image:
        masks.append(np.array(image.convert("L")) > 127)

assert rgb[0].shape == rgb[1].shape, "서로 다른 크기/구도의 실행입니다."
assert masks[0].shape == masks[1].shape
print("RGB 완전 동일:", np.array_equal(rgb[0], rgb[1]))
print("실제 RGB 변경 픽셀:", int(np.any(rgb[0] != rgb[1], axis=2).sum()))
print("옷 마스크 차이 픽셀:", int(np.logical_xor(masks[0], masks[1]).sum()))
```

### 6단계: 작아진 마스크 밖에 옷이 남는지 확인

`target_mask.png`와 `adjusted_overlay.png`를 같은 배율로 본다.
`repair_mask.png`가 표시하는 영역에 기존 옷 색·줄무늬·밑단이 남아 있는지 확인한다.
남아 있다면 목표선 계산이나 S/M/L 선택보다 복원 품질 문제가 우선이다.
실제 사진에서는 테스트 이미지의 빨간색 임계값을 재사용하지 말고 육안 확인 또는 별도 옷 경계 검증을 한다.

### 7단계: 새 DM-VTON 경로에서도 같은 기준으로 확인

`render_sizes()`가 표의 각 행을 순회하고 서로 다른 `length_ratio`, `chest_ratio`,
`target_hem_y`, `target_width_px`를 만드는지 확인한다.
현재 수치는 `run_comparison()`의 세션 캐시 `size_reports`에 보관되며,
기존 FASHN 화면의 `synthesis.json` 저장 기능이 새 화면에도 있다고 가정하면 안 된다.
기본 합성 갤러리 항목이 아니라 S/M/L 캡션이 있는 결과끼리 비교한다.
자동 마스크가 소매·팔·다른 옷을 포함하는 문제와 복원 잔상도 따로 확인한다.

## 5. 현재 확정 범위와 후속 판정 기준

확정한 것은 기본 합성의 치수 입력 부재, 기존 UI의 별도 적용/초기화 동작,
통제 이미지에서 후처리 출력의 사이즈별 차이, 축소 복원의 옷 색 번짐이다.
당시 사용자가 어떤 출력 칸을 보았는지, 후처리를 실행했는지, Colab에서 같은 코드가 실행됐는지는
아직 확정하지 않았다. 이전 결과 파일과 실행 셀을 확보하면 위 절차로 구간을 좁힐 수 있다.

다음 검증 완료 조건은 **같은 기본 합성에서 서로 다른 목표 좌표가 만들어지고, 변형 마스크와
실제 조정 이미지의 옷 경계가 그 변화에 따라 움직이는지**다. 이 조건을 만족한 뒤에야
실제 착용 사진과의 치수·굴곡·핏 정확도 평가로 넘어갈 수 있다.
