## 최신 사이즈 추천 방향 (2026-10-25, 기준 옷 입력부터)

사용자가 잘 맞게 입는 상의가 있으면 그 옷의 **총장·어깨너비·가슴단면(cm)**을
새 옷의 각 판매 사이즈와 비교하는 방향으로 전환했다. 기준 옷이 없으면 사용자가
입력한 성별·키·체중과 `size_data`의 엑셀 실측 자료로 신체 치수 범위를 예측하는
경로를 사용한다. 옷 치수는 몸 치수로 환산하지 않는다.

1단계 직접 입력: `app/reference_garment.py`는 세 항목의 누락,
0 이하, 숫자가 아닌 값, 무한대·NaN을 거부하고 옷 치수를 그대로 보관한다.
`python -X utf8 scripts/debug_reference_size.py --ui`로 기본 포트 7863의 웹 화면을
실행한다. 입력 확인 후 세션에 보관하고, 수정하면 확인값을 비운다. 새로고침 시
다시 입력한다. 아래 2단계 엑셀 모델 디버거도 추가했다. 기준 옷 입력과 신체 예측은 별도
화면이다. 새 옷 수동 치수 비교는 아래 통합 화면에 연결했고, OCR·마스킹·합성 조정은 후속 단계다.

### 새 옷 판매 사이즈표 입력·치수 비교 완료 (2026-10-25)

`app/garment_compare.py`와 `scripts/debug_size_compare.py`에서 기존 입력 경로를 연결했다.
사진 표시나 굴곡 보정에 앞서 판매 사이즈별 총장·어깨너비·가슴단면을 직접 입력하고 차이를 확인한다.
실제 판매 라벨과 입력 행 순서를 유지하며, 완전히 빈 행은 무시하고 부분 누락·중복 사이즈·
0 이하·NaN/무한대는 거부한다. 단위는 cm, 가슴은 펼친 옷의 가슴단면이다.

- **기준 옷 경로**: 새 옷 − 기준 옷으로 총장·가슴단면 차이를 계산한다. 두 옷 모두 일반 어깨선으로
  확인했을 때만 어깨 차이를 계산한다. 드롭숄더·래글런·구조 미확인은 수치를 보존하고 비교는 보류한다.
- **기준 옷이 없는 경로**: 키·체중·선택 성별로 기존 저장 Ridge 모델을 실행한다. 예측 신체 기준
  총장은 `목뒤높이 - 위앞엉덩뼈가시높이`이며, 기본 길이 차이는 옷 총장에서 이 예측값을 뺀다.
  가슴 단면 여유는 `옷 가슴단면 - 몸 가슴둘레/2`, 둘레 여유는 그 두 배다. 신체 예측 범위의
  상한을 빼서 여유의 하한을 계산한다. 실제 밑단 이동량·정면 가슴너비·마스크 이동량으로 해석하지 않는다.
- 신체 어깨사이너비와 옷 어깨너비는 정의 차이로 별도 표시한다. 적정 여유분 기준을 검증하기 전까지
  고정 기준으로 S/M/L을 확정하지 않는다. 학습 범위 밖 입력은 기존 예측 보류를 유지한다.
- 입력 변경 시 이전 결과·다운로드를 비운다. 저장하면 `outputs/size_compare/<실행시각>/`에
  원본 입력·출처·모델 경로·예측 범위·치수 차이 JSON과 보고서를 보존한다. 모델은 신체 예측 경로에서만
  불러오며 재학습하지 않는다. `가상 예시 채우기`는 디버깅용이며 실제 상품 치수가 아니다.

```powershell
python -X utf8 scripts/debug_size_compare.py --ui
```

웹 주소는 `http://127.0.0.1:7866`이다. 비교 기준 선택 → 기준 옷 또는 착용자 정보 입력 →
새 옷 판매 사이즈표 입력 → **치수 비교** 순서다. OCR과 사진 윤곽·마스킹·합성 조정은 후속 단계다.

옷 단면·몸 둘레 구분, 예측 범위의 차이 전파, 어깨 비교 보류, 잘못된 입력, 출처 보존·저장과
모델 없는 기준 옷 경로를 다루는 새 테스트 11개와 기존 기준 옷 테스트 5개를 통과했다.
실제 웹 API에서 저장 Ridge 모델의 예측·범위 밖 입력·중복 사이즈 거부를 확인했고, 브라우저에서
두 모드 전환·예시 입력·치수표 셀 편집·입력 변경 시 결과 초기화와 재계산을 확인했다.

### 목표 윤곽 1~3단계 웹 디버거 (2026-10-25)

바꾸면 목표선을 다시 계산한다. 함께 채운 새 옷 표는 가상 테스트 값이며 실제 상품 치수로 교체한다.

- `ratio_v0`: 기준 사진 목→밑단 거리에 새 옷/기준 옷 총장 비율, 몸통 횡방향 좌표에 가슴단면 비율을
  적용한다. 사진의 목→밑단 축을 유지하며 확인한 부위만 변형한다. 어깨는 양쪽 옷의 일반 어깨선과
  봉제선 두 점을 확인할 때만 적용한다. 자동 분할·굴곡·처짐·원근 보정이나 실제 핏 재현은 아니다.

- 저장은 현재 입력으로 재계산하고 `outputs/size_preview/<실행시각>/`에 `fit_plan.json`,
  `comparison.json`, `reference.png`, `overlay.png`, `report.md`를 만든다. 사진 해시·기준점·확인 상태·
  치수·선택 사이즈·적용 비율로 결과를 재현할 수 있다. 기존 실행은 덮어쓰지 않는다.

아래 후속 요청으로 같은 화면에 기본 합성·옷 영역 조정 실험을 추가했다.
같은 사람이 대상 옷을 실제로 입은 사진이 필요한 정량 오차 검증은 자료 확보 후 진행한다.

관련 테스트는 새 윤곽 테스트 10개와 기존 치수 비교·기준 옷 테스트 16개가 통과했다.

다른 사진 업로드 후 5점 수동 입력·확인을 확인했다. 이는 기능 검증이며 실착 정확도 평가가 아니다.

### 기본 합성 → 목표 윤곽 후처리 실험 (2026-10-25)

`app/size_synthesis.py`, `scripts/size_synthesis_ui.py`를 7867 웹 디버거의 4단계로 연결했다.
사용자 요청에 따라 이 화면의 드롭숄더·래글런 등 어깨 구조 선택창과 어깨 변형 옵션을 제거했다.
어깨 치수 입력·기록은 유지하고 총장·몸통 폭만 조정한다. 기존 합성 엔진은 FASHN이며 CATVTON으로
교체하지 않았다. FASHN에 사이즈표/목표 마스크를 직접 조건으로 주는 방식은 아니다.

1. 1~3단계에서 기준 옷·사진·치수를 확인하고 목표선을 만든다.
2. **새 옷 상품 사진**을 올리고 **FASHN 기본 합성 생성**을 누르거나, 다른 GPU 환경의 기본 합성 결과를
   업로드한다. 원본과 같은 구도·가로세로 비율이어야 한다. 사이즈를 바꿀 때 이 기본 합성을 재사용한다.
3. 초록색 GrabCut 옷 영역 초안을 확인하고 브러시/지우개로 수정한다. 피부·바지·배경을 제외하고 확인한다.
   기본 합성은 특정 상품 사이즈를 정확히 재현했다고 가정하지 않으며 실제 밑단과 폭을 마스크에서 읽는다.
4. **선택 사이즈 적용**으로 확인한 옷 영역을 목표선에 맞춘다. 목·어깨 부근은 고정하고 몸통에 폭 변형을
   점진적으로 적용한다. 총장 감소로 드러난 영역은 OpenCV Telea로 복원하며 복원 마스크를 따로 보여준다.
   옷 무늬 변형·팔 침범·복원 흔적은 육안 검증 대상이다. 편집 영역 밖은 기본 합성과 화소 단위로 동일하다.
5. **현재 합성·사이즈 조정 실험 저장**은 현재 사이즈·마스크로 다시 계산하고 새 실행 폴더에 저장한다.
   `person.png`, `base.png`, `adjusted.png`, `source_mask.png`, `target_mask.png`, `repair_mask.png`,
   `adjusted_overlay.png`, 선택적 `garment.png`, `synthesis.json`, `report.md`를 보존한다.

GPU 없는 로컬에서는 **GPU 없이 기준 사진으로 변형 시험**을 사용한다. 이 결과의 출처는
`reference_photo_dry_run`이며 새 옷 합성 결과로 표시하지 않는다. 외부 업로드는 `external_unverified`로
엔진·시드 미확인을 기록한다. 직접 FASHN 생성은 설정·시드·입력/출력 해시·시간을 기록한다.

CPU 환경의 별도 의존성은 `requirements_size_preview.txt`다. 이 PC에는 FASHN과 CUDA GPU가 없으므로
새 옷 생성은 준비된 GPU 환경에서 실행해야 한다. 이 도구는 설치/가중치 다운로드를 수행하지 않으며,
FASHN 호출은 `HF_HUB_OFFLINE=1`인 별도 프로세스로 실행해 파서의 추가 다운로드도 막는다.

```powershell
python -X utf8 scripts/debug_size_preview.py --ui
```

기존 서버가 7867을 사용 중이면 종료 후 다시 실행하거나 `--port 7877`을 붙여 새 화면을 연다.
가중치와 파서 캐시가 이미 준비된 GPU 환경에서는 기본 합성만 별도로 생성할 수 있다.

```powershell
python -X utf8 scripts/run_size_synthesis.py --person person.png --garment garment.png --output outputs/base_run
```

현재 검증은 생성 호출 경계의 테스트, CPU 옷 영역 변형·복원·저장과 브라우저 동작까지다.
실제 FASHN GPU 생성과 실제 대상 옷 착용 사진 대비 정확도는 아직 검증하지 않았다.
새 합성 테스트 9개와 기존 관련 테스트 42개가 통과했다. 브라우저에서 00_ME의 S→L 전환 시
기본 사진·확인 마스크 재사용, 결과 초기화·재적용, 마스크 수정 시 확인/결과/다운로드 초기화와
현재 사이즈 저장을 확인했다. 실제 저장 결과에서 편집 영역 밖 최대 화소 차이는 0이었다.

기본 엔진의 가중치·출력 크기 처리와 파서 로딩은
[FASHN 공식 파이프라인](https://github.com/fashn-AI/fashn-vton-1.5/blob/main/src/fashn_vton/pipeline.py),
파서 캐시는 [공식 가중치 준비 스크립트](https://github.com/fashn-AI/fashn-vton-1.5/blob/main/scripts/download_weights.py)를 확인했다.

### 2단계 엑셀 신체 모델 비교 완료 (2026-10-25)

현재 세부 목표는 `AGENTS.md`가 우선한다. 신체 예측 입력은 성별·키·체중이고 첫 예측
대상은 **어깨사이너비·신체 기준 총장·가슴둘레** 세 개다. 어깨사이길이는 과거 자료로
보존하되 이번 학습 대상에서 제외했다. 신체 기준 총장은 `목뒤높이 - 위앞엉덩뼈가시높이`다.
이 신체 예측을 옷 실측과 비교해 어깨 마스킹·합성 세로 길이·가슴 영역 조정에 활용하는
목표가 추가됐지만, 조정 로직 자체는 아직 구현하지 않았다.

`size_data/전처리데이터.xlsx`의 `전처리` 시트(헤더 2행), 5,092명 자료를 사용했다.
cm/kg 단위와 총장 계산은 간소화 원자료와 전원 대조해 일치했다. 학습 로더에서도
단위 헤더·양수 유한값·특수 코드·중복 ID를 검사했다. 이번 실행의 제외 행은 0개다.

- 입력 특성은 키·체중 두 개이며 성별로 모델을 분리한다. ID와 정답 치수는 특성에서 제외한다.
- 성별 비율을 유지해 학습 3,054명·범위 보정 1,019명·최종 평가 1,019명으로 고정 분할했다.
- 학습 자료의 5-fold CV MAE로 성별 평균·Ridge·Gradient Boosting을 비교했다.
  Ridge는 fold 안에서 표준화하고 alpha를, Boosting은 트리 수·깊이를 작은 격자로 탐색했다.

### 목표와 범위

이번 단계는 **상의 사이즈 추천**이다. 사용자 정면 전신 사진과 키로 어깨너비·가슴둘레를
가능한 범위로 추정하고, 사용자가 올린 **새 옷의 치수표**와 비교해 S/M/L 등 실제 판매
사이즈를 추천한다. 허리·엉덩이·하의 추천은 제외한다. 새 옷 합성 단계나 S/M/L별 착용
이미지는 구현하지 않는다. 기존 FASHN 합성 기능은 유지하되 이 추천 흐름과 독립적으로 둔다.

사용자가 잘 입는 **레귤러핏 반팔 치수표**는 선택적인 보정 자료이다. 이것이 없어도
유효한 전신 사진으로 체형을 추정한다. 다만 **대상 상품 치수표가 없으면 상품별 사이즈는
추천할 수 없다**. 이때는 추정한 몸 치수와 필요한 추가 입력만 보여준다.

### 사용자 흐름

1. 정면 전신 사진과 키(cm)를 받는다. 사진이 잘렸거나 자세/랜드마크/척도 판단이
   불가능하면 이유를 보여주고 재업로드를 요청한다. 어깨너비 자체가 무효라면
   어깨 기반 가슴 대체값도 만들지 않는다.
2. 유효한 사진에서 어깨너비를 추정한다. 가슴 경계가 분리되면 가슴둘레의 추정
   범위를 계산한다. 소매·팔·오버핏과 섞여 경계가 불명확하면 사진 가슴값은 버린다.
3. 가슴 경계가 불명확할 때에만 사용자가 선택한 남/녀 **측정 기준**과 어깨너비를
   이용해 통계적으로 검증된 평균 가슴둘레 **범위**를 제시한다. 성별은 사진으로
   판정하지 않는다. 선택을 원치 않거나 검증 데이터가 없으면 직접 가슴둘레를
   입력받는다. 직접 입력값은 본인 실측인지 자가 추정인지 구분한다.
4. 선택 입력: 평소 적당하게 입는 레귤러핏 반팔의 치수표 이미지, 실제 착용
   사이즈, 착용감(작음/적당함/큼)을 받는다. OCR 결과를 원본 이미지와 함께
   보여주고 사용자가 치수·단위·라벨을 확인/수정한다. 치수표 없이 S/M/L 레이블만
   알려주는 것은 몸 치수 보정 근거가 아니므로 보정하지 않는다.
5. 새 옷의 치수표 이미지 또는 검증된 구조화 데이터를 받는다. OCR 결과를
   확인/수정받고, 가슴 항목이 빠졌거나 단면/둘레가 모호하면 추천 전에 수정 요청한다.
6. 모든 판매 사이즈별 가슴 여유분과 비교 가능한 경우 어깨 여유분을 제시한다.
   추정 범위에서 추천이 안정적이면 한 사이즈, 경계에 걸리면 복수 후보와
   구분에 필요한 입력(직접 가슴 실측 또는 기존 옷 치수표)을 제시한다.

### 추천 계산과 안전장치

- 가슴 여유분은 `옷 가슴단면 - 몸 가슴둘레 / 2`로 계산한다. 몸 둘레가 범위이면
  각 사이즈 여유분도 범위이다. 가슴을 주요 기준, 어깨를 보조 기준으로 둔다.
- 옷 어깨너비는 드롭숄더·래글런·기타 패턴에 따라 몸 어깨너비와 의미가 다르다.
  일반적인 봉제 어깨선인지 확인되지 않으면 점수에서 제외하고 제외 사유를 표시한다.
- 기존 옷의 치수+착용감은 가능한 몸 둘레 또는 개인 선호 여유를 좁히는 **제약**으로
  쓴다. 기존 옷의 가슴단면을 곧장 사용자 가슴단면으로 치환하지 않는다.
  착용감별 여유 범위는 실제 사례로 보정하기 전까지 고정 사실로 주장하지 않는다.
- 체형 범위 전반에서 같은 사이즈가 조건을 만족하면 단일 추천. 적합 사이즈가
  갈리거나 사진·표의 불확실성이 크면 후보들을 나란히 보여주며 직접 실측을 권한다.
  필수 치수 누락·단위 미확인·사진 무효 시 숫자를 채워 넣어 추천하지 않는다.
- 결과에는 사용한 몸 치수의 출처, 사진 실패 여부, OCR에서 수정한 항목,
  사이즈별 가슴/어깨 여유, 추천 근거와 한계를 함께 표시한다.

### 검증·발표 기준

- 어깨 계수 `1.28`이나 개인 사진에서 조정한 `1.33`을 보편적 실측 정확도로
  취급하지 않는다. 평균 가슴 대체 계수와 불확실성 폭도 실측 짝 데이터 및
  홀드아웃 검증으로 정하기 전까지 미정이다.
- 정상 사진, 오버핏으로 가슴 경계가 보이지 않는 사진, 전신이 잘린 사진,
  OCR 오독, 가슴단면/옷둘레/권장 신체둘레 혼동, 어깨가 특수한 옷,
  M/L 경계 사례를 각각 테스트한다. 직접 실측과 비교한 오차·추천 일치율뿐
  아니라 `재업로드`, `수동 입력`, `복수 후보` 비율도 기록한다.
- 실패 사례와 재현 입력 조건은 발표 근거로 남긴다. 검증되지 않은 평균이나
  자동 추천을 실제 신체 실측과 동등하게 광고하지 않는다.

### 구현 순서

1. 두 치수표의 역할, 몸/옷 단위, 출처·범위 자료형과 테스트를 정의한다.
2. 사진 품질 게이트와 어깨/가슴 추정의 성공·실패 경로를 분리한다.
3. 평균 가슴 대체 관계를 실측 데이터로 검증하거나, 없으면 직접 입력 경로만 둔다.
4. OCR/Vision 호출 및 사용자 확인/수정 UI를 붙인다.
5. 기존 반팔 보정과 대상 상의 범위 기반 추천을 구현한다.
6. 합성 없이 사이즈 추천만 실행해 위 실패 케이스와 실측 정확도를 검증한다.

### 속도 최적화 — "기술적 기여"로 발표할 부분
P100 기준 실측. 실제 쇼핑몰 상품 3벌로 검증 완료.

| 설정 | 시간 | 배속 | 옷 재현 |
|---|---|---|---|
| DDIM 30 + CFG on (원본 설정) | 103초 | 1.0x | 기준 |
| **DPM++ 8 + CFG on (현재 기본값)** | **29초** | **3.5x** | **유지됨** |
| DPM++ 4 + CFG on | 15.7초 | 6.6x | 사진 프린트가 쪼그라듦 |
| DPM++ 8 + CFG off | 16.2초 | 6.4x | **사진 프린트 옷 붕괴** |
| DPM++ 4 + CFG off | 9.3초 | 11.1x | **사진 프린트 옷 붕괴** |

**샘플러 교체(DDIM→DPM++)가 안전한 가속이고, CFG 끄기는 아니다.**
DDIM은 스텝을 줄이면 무너지지만(4스텝 SSIM 0.895) DPM++는 8스텝에서 유지된다.
반면 CFG를 끄면 시간은 정확히 절반이 되지만 옷 재현이 깨진다 — 무지 바지는 멀쩡하고
큰 글자 프린트는 흐려지는 정도인데, **사진 프린트 티셔츠는 알아볼 수 없게 뭉개졌다.**

#### 스텝 수를 더 줄일 수 있나 (실측)
20초 미만을 목표로 5·6스텝까지 내려봤다. P100 기준.

| 스텝 | P100 | T4 환산 | 옷 영역 SSIM (티셔츠) | 사진 프린트 재현 |
|---|---|---|---|---|
| 30 | 102.8초 | 73초 | 1.000 | 기준 |
| **8** | **29.1초** | **약 21초** | **0.953** | **유지됨** |
| 6 | 22.5초 | 약 16초 | 0.922 | **프린트 주제가 사라짐** |
| 5 | 19.1초 | 약 14초 | 0.859 | 사라짐 |
| 4 | 15.8초 | 약 11초 | 0.820 | 사라짐 |

무지 바지와 큰 글자 프린트는 4스텝에서도 쓸 만하지만, **사진 프린트 티셔츠는
6스텝에서 오랑우탄 그림이 통째로 사라지고 말풍선만 남는다.** 8스텝이 하한선이다.
→ 스텝을 줄이는 방식으로는 20초 미만을 못 맞춘다. 품질을 유지한 채 줄이려면
샘플링 스텝이 아니라 **스텝당 비용**(attention 구현, channels_last, torch.compile)을
건드려야 한다.

※ T4 환산은 이전 측정에서 얻은 비율(T4 ≈ P100 × 0.71)로 계산한 값이며 직접 재지 않았다.

#### 스텝당 비용 줄이기 — 절반만 확인됨
CatVTON 원본은 이미 SDPA attention · fp16 · `torch.no_grad` · TF32를 쓰고 있어
손댈 것이 별로 없었다. 남은 후보는 `channels_last` 와 `torch.compile` 둘.

| 설정 | P100 확산 시간 | 기준과 옷 SSIM |
|---|---|---|
| 기준 | 28.2초 | 1.0000 |
| channels_last | 28.3초 | 1.0000 |
| torch.compile | 28.3초 | 1.0000 |
| 둘 다 | 28.3초 | 1.0000 |

- **channels_last: 효과 없음** (P100 실측). 결론 낼 수 있다.
- **torch.compile: 아직 결론 못 냄.** Inductor가 쓰는 Triton은 compute capability
  7.0 이상을 요구하는데 P100은 6.0이라 조용히 eager로 되돌아간다
  (docs/ENVIRONMENT.md #10). **T4(7.5)에서 다시 재야 한다.**
- 부수 소득: 세 설정 모두 기준과 옷 SSIM이 1.0000이었다. "구현만 바꾸면 결과가
  같다"는 전제는 검증됐으므로, 빨라지는 설정을 찾으면 품질 검증은 끝난 셈이다.


#### SSIM의 한계 (발표에서 말할 것)
붕괴한 티셔츠의 SSIM은 0.950으로, 멀쩡한 맨투맨(0.953)과 사실상 같았다.
**인물과 배경이 화면의 대부분이라 옷이 망가져도 SSIM이 거의 안 움직인다.**

그래서 AutoMasker가 만든 **옷 마스크 안쪽 픽셀만** 재도록 바꿨다. 같은 이미지들을
두 지표로 재면 차이가 뚜렷하다 (티셔츠, 30스텝 대비):

| 스텝 | 전체 SSIM | 옷 영역 SSIM |
|---|---|---|
| 8 | 0.990 | 0.953 |
| 6 | 0.982 | 0.922 |
| 5 | 0.969 | 0.859 |
| 4 | 0.961 | 0.820 |

전체 SSIM은 0.99~0.96 사이에서만 움직여 판단 근거가 안 되는데,
옷 영역 SSIM은 0.95~0.82로 벌어져 눈으로 본 열화와 방향이 맞는다.
다만 이것도 완벽하지 않다 — 맨투맨은 4스텝에서 옷 SSIM이 0.764까지 떨어지지만
글자는 여전히 읽힌다. **최종 판단은 눈으로 한다.**

**A안이 설득력을 가지려면 "안 되는 걸 막는 장치"가 핵심이다.** 사용자가 프린트 티를 올렸을 때

### A. 합성과 사이즈 추천을 연결 — ~~가장 큰 구멍~~ 범위 축소
> **2026-09-14 확정: 사이즈별 착용 이미지는 만들지 않는다 (요청 시 생성 옵션도 폐기).**
> 합성 모델은 옷 사진만 보고 그리므로 S와 L의 핏 차이를 정확히 표현할 수 없고, 아래 1·2번처럼
> 옷·마스크를 늘려도 물리적 근거가 없다. 틀린 핏 이미지는 사이즈 추천의 신뢰를 오히려 깎는다(리스크 큼).
> 사이즈 차이는 **치수표 비교 결과(부위별 여유: 딱 맞음 / 여유 있음 / 끼일 수 있음, S/M/L 표)로만** 보여준다.
> 발표에서는 "이미지는 어울림, 치수 비교는 사이즈"로 역할을 나눈 설계로 설명한다.
> 아래는 원래 검토했던 접근(기록용)이다.
지금은 두 기능이 **따로 논다**. 사진 합성은 사이즈를 모르고, 사이즈 추천은 그림에 반영되지 않는다.
계획서 세부계획 3번의 *"여유분 값으로 실루엣 폭 조절"* 이 두 파트를 잇는 다리인데 미구현이다.

발표에서 "사이즈를 반영한 가상 피팅"이라고 말하려면 이게 있어야 한다. 접근 후보:
1. 사이즈별로 옷 이미지를 여유분 비율만큼 가로 스케일 조정 후 합성 (구현 쉬움, 물리적 정확도 낮음)
2. 마스크를 여유분만큼 넓혀서 합성 (실루엣이 실제로 넓어짐)
3. S/M/L 각각 합성해 나란히 비교 (가장 단순하고 시연 효과는 확실)

### B. 옷 치수표 데이터 확보
현재 `data/size_charts/`에 예시 2개뿐이다. 실제 쇼핑몰 상품의 치수표를 옷 이미지와 짝지어

### C. 실제 사진 테스트 — 1차 완료
팀원 사진 3장(정자세 / 팔 벌림 / 엄지척) × 옷 3벌 = 9건을 돌렸다.
결과는 `data/samples/results/real_person/` (사진은 저작권·개인정보상 커밋 제외).

**잘 된 것 — 걱정했던 것보다 낫다**
- 얼굴·손·자세·배경이 그대로 보존된다
- **팔 겹침(엄지척)이 문제가 안 됐다.** 손이 가슴 앞에 있어도 손가락이 살아있고
  옷이 손 뒤로 자연스럽게 들어간다. 계획서에서 가장 걱정한 항목인데 통과다
- 복도·패턴 바닥·유리벽 같은 복잡한 배경도 영향 없다
- 마스크는 세 자세 모두 정확하게 잡혔다

**실패 1 — 하의 색이 틀린다 (재현성 있음)**
네이비 코듀로이 바지가 인물에 따라 **크림색 / 회청색**으로 나온다. 세 번 다 틀렸다.
마스크는 정상이므로 확산 단계 문제다. 데모 인물에서는 같은 옷이 어두운 네이비로
제대로 나왔으므로 **인물 사진에 따라 달라진다**.
- 옷 사진 프레이밍 탓이 아니다: 바지가 이미지의 63%를 차지해 셔츠(60%)와 비슷하다
- 원인 미확인. 스텝을 30으로 올리거나 guidance를 높여서 갈리는지 봐야 한다

**실패 2 — 프린트 재현이 인물마다 다르다**
같은 오랑우탄 티셔츠인데 엄지척 사진에서는 프린트가 살아나고 나머지 둘에서는
거의 사라진다. 옷이 같고 설정이 같으므로 **인물 의존성**이다.

**원인 규명 완료 — 파이프라인에 빠진 단계가 있었다**

guidance를 올리면 하의 색이 실제로 맞아갔다(크림색 → 데님 블루). 그런데 동시에
**얼굴이 일그러지고 배경이 물감처럼 번졌다.** 옷만 바꾸면 되는데 왜 배경까지 망가지나?

CatVTON 파이프라인은 latent 전체를 디코딩해 돌려준다. 즉 **마스크 밖도 다시 생성한다.**
인페인팅이라면 마스크 밖은 원본 픽셀을 그대로 써야 하는데 그 단계가 없다. 그래서
얼굴·손·배경이 VAE를 왕복하며 뭉개지고, guidance를 올리면 그 열화가 증폭됐다.
**"옷을 강하게 반영"과 "나머지를 지킨다"가 맞바꿀 수밖에 없는 구조였던 것이다.**

`Image.composite(result, person, mask)` 한 줄로 마스크 밖을 원본으로 되돌렸다
(`app/tryon_core.py`의 `composite` 인자, 기본 켬). 결과:

| 설정 | 하의 색 | 얼굴·배경 |
|---|---|---|
| 합성없음 g2.5 (종전) | 크림색 (틀림) | 미세하게 뭉개짐 |
| 합성없음 g5.0 | 데님 (맞음) | **완전히 망가짐** |
| **합성 g5.0** | **데님 (맞음)** | **원본 그대로** |

→ ~~하의 색 문제 해결. 부위별 guidance 기본값을 두었다(상의 2.5 / 하의 5.0).~~
   **(2026-09-13 번복)** 단색 올리브 바지에서 5.0이 위장무늬 얼룩을 만들고 2.5가 깨끗했다.
   코듀로이 한 벌로 정한 기본값이었다. 하의도 2.5로 되돌렸다. 아래 F-2 참고.
   상의는 5.0으로 올리면 오히려 가장자리가 지저분해져 2.5가 낫다.

**남은 문제 — 모델 한계가 아니라 시드 불안정성이었다**

"프린트가 재현되지 않는다"고 두 번 적었는데 틀렸다. 설정을 전부 고정하고
**시드만 6개로 바꿔보니 seed 123에서 오랑우탄이 선명하게 나왔다.**

| | 결과 |
|---|---|
| 오랑우탄 프린트 (g2.5) | 6개 시드 중 **1개 성공** |
| 하의 색 (g2.5) | 6개 중 0개 정확. 2개가 옅은 파랑, 1개는 치마 형태로 붕괴 |

즉 이 모델은 **같은 입력에 대해 결과가 크게 흔들린다.** 앞서 "인물에 따라
갈린다"고 본 것도(데모 인물·_01에서는 나오고 _02에서는 안 나옴) 실은 시드 운이었다.
스텝을 30으로 올리고 guidance를 7.5까지 올려도 안 나왔던 이유는, 그 조합들이
전부 seed=42 한 장의 뽑기였기 때문이다.

**말풍선 글자는 거의 항상 재현된다.** 따라서 "세밀한 프린트가 한계"라고
적었던 것도 틀렸다. 작은 글자는 되고 큰 그림이 흔들린다.

**저장소 기본값(DDIM 50스텝)으로도 안 나온다 — 스텝은 원인이 아니다**

"GitHub 예시처럼 안 나오는 게 우리가 8스텝을 써서인가"를 확인하려고 저장소 데모 앱의
기본값(DDIM 50스텝, guidance 2.5, 마스크 밖 복원 없음)을 그대로 재현했다.

| 설정 | 시간 | 오랑우탄 | 하의 색 |
|---|---|---|---|
| 저장소 그대로 DDIM 50 | 169.5초 | ❌ | 크림색 |
| DDIM 50 + 합성 | 169.6초 | ❌ | 크림색 |
| DPM 50 + 합성 | 169.6초 | ❌ | 크림색 |
| DPM 30 + 합성 | 102.8초 | ❌ | 크림색 |
| **DPM 8 + 합성 (현재)** | **29.3초** | ❌ | 크림색 |
| DPM 50 g5.0 + 합성 | 169.7초 | ❌ | 옅은 파랑 |

**여섯 설정이 사실상 구별되지 않는다.** 스텝을 8에서 50으로 6배 올려도 달라지는 게 없다.
반면 시드 하나만 바꾸면 오랑우탄이 나온다. **변동의 주된 요인은 스텝이 아니라 시드다.**

부수적으로 이것은 8스텝 기본값을 뒷받침한다. 50스텝은 5.8배 느린데 이 사진들에서
얻는 것이 없다.

→ **대응이 완전히 달라진다.** 모델을 바꿀 문제가 아니라, 여러 장을 뽑아
   고르게 하는 문제다. 8스텝이면 T4에서 한 장 18초이므로 3~4장을 뽑아
   나란히 보여주는 것이 현실적이다. UI에 **다시 생성 / 여러 장 후보** 를 넣는다.
   이 관점에서 보면 앞서 한 속도 최적화(103초 → 18초)가 품질 대책이 된다 —
   빠르니까 여러 번 뽑을 수 있다.

### D. 여유분 기준값 검증
`size_fit.FIT_BANDS`의 타이트/레귤러/루즈 구간은 일반적인 쇼핑몰 가이드를 참고한 값이지
측정으로 얻은 값이 아니다. 실제 옷 몇 벌을 입어보고 "이 여유분일 때 이런 핏"을 대조하면
근거가 생긴다.

### E. 품질 평가 보강
SSIM은 "베이스라인과 같은 그림인가"만 잰다. 사람 5~10명 A/B 설문 하나만 있어도
"가속해도 품질이 유지된다"는 주장이 방어된다.

### 판정 기준 (합격/불합격을 이걸로 매긴다)

"뭔가 나오면 성공"으로 보면 개선 여부를 판단할 수 없다. 아래를 **전부** 만족해야 합격.

1. **색조**가 원본 옷과 같은가 (밝기·채도까지)
2. **프린트/무늬**가 원본과 알아볼 수 있게 같은가 (형태·위치·크기)
3. 원본에 **없던 얼룩·흰 자국**이 없는가
4. **실루엣**이 옷 종류에 맞는가 (긴팔→긴팔, 바지→바지)
5. **얼굴·손·배경**이 보존되는가

이 기준으로 현재 상태를 매기면 **18건 중 2건 합격** (파란 맨투맨 · 배경 그대로 · seed 123/7).
나머지는 색조가 다르거나(바지), 프린트가 뭉개지거나(티셔츠), 소매에 흰 얼룩이 생겼다(셔츠·흰 배경).

### F-0. 배경 정규화 — 부분적으로만 효과 (검증 중)

**문제.** CatVTON은 VITON-HD/DressCode로 학습됐고 이 데이터셋은 전부 흰 배경
스튜디오 촬영이다. 우리 사진은 복도·패턴 바닥·유리벽이라 분포 밖이고,
그래서 옷 재현 성공률이 떨어진다.

**재학습은 불가능하다.** 가상 피팅 학습에는 (인물, 옷, 그 사람이 그 옷을 입은 사진)
3종 세트가 필요한데, 그건 사람을 세워두고 옷을 갈아입혀 가며 촬영해야 만들어진다.
종설 범위가 아니고, 문제는 GPU가 아니라 데이터다.

**대신 입력을 모델 쪽으로 밀었다.** SCHP 인물 파싱으로 사람만 오려 흰 배경에
올려서 합성하고, 원래 배경은 마스크 밖 복원으로 되돌린다. AutoMasker가 이미
돌리는 파싱을 재사용하므로 추가 모델도 의존성도 비용도 없다.

**결과 — 옷에 따라 갈린다. 깨끗한 승리가 아니다.**

| 옷 | 배경 그대로 | 흰 배경 | 위 기준 판정 |
|---|---|---|---|
| 사진 프린트 티셔츠 | 프린트 없음 | 프린트 생기나 **뭉개짐** | 둘 다 불합격 (기준 2) |
| (티셔츠 +8px 팽창) | — | 어깨에 새 얼룩 | 불합격 (기준 3) |
| 긴팔 맨투맨 | 깨끗함 | **소매에 흰 얼룩** | 배경 그대로만 합격 |
| 데님 바지 (g5.0) | 1건 붕괴·1건 얼룩 | 형태는 안정 | 둘 다 불합격 (기준 1, 색조가 밝은 워싱) |

**긴팔 셔츠가 나빠지는 이유**: 팔이 몸통에서 떨어져 있으면 팔 옆의 흰 배경이
소매 안으로 번져 들어온다. 후광을 바깥에서 잡았더니 안으로 들어온 셈이다.
**실루엣을 8px 넓혀봤지만 실패했다.** 흰 얼룩이 그대로 남고 오히려 어깨에
새 얼룩이 생겼다(`data/samples/results/grow/`). 흰색을 옷에서 물리적으로
떼어놓는 것으로는 해결되지 않는다.

메커니즘이 분명해졌다. **옷 마스크가 팔처럼 가느다란 부위를 덮을 때** 그 안으로
흰 배경이 끌려 들어온다. 반팔 티셔츠는 마스크가 몸통 위주라 안전하고,
긴팔은 마스크가 팔을 덮어서 망가진다. 즉 **옷 종류에 따라 안전/위험이 갈린다.**

→ 기본값은 꺼 둔다. 켜려면 상의 중에서도 반팔처럼 마스크가 몸통에 한정되는
   경우로 좁혀야 하는데, 그걸 미리 알 수 없다.

**바지 개선은 배경이 아니라 guidance 5.0 덕분이다.** 배경 정규화의 공로가 아니다.

구현에서 걸린 것: 옷 마스크가 blur 때문에 인물 실루엣보다 바깥으로 번져 있어,
그 띠에 흰 배경이 들어가 **인물 주위에 흰 후광**이 생겼다. 합성 마스크를
인물 영역과 교집합으로 제한해 해결했다.

인물 파싱이 실패하면(영역이 화면의 10% 미만이거나 90% 초과) 자동으로 건너뛴다.

### F-1. 옷 색 보정 — 부분 성공, 기준 미달

확산 설정으로 하의 색을 못 맞춰서(크림 → 밝은 워싱 데님, 어느 설정도 다크
네이비를 못 냄), 정답 색이 입력 옷 사진에 있다는 점을 이용해 후처리로 맞췄다.
LAB에서 중앙값·MAD를 맞추되 밝기 산포는 유지해 주름과 음영을 살린다.

구현 중 버그가 두 번 났고 둘 다 목표 색 추정 문제였다.
1. 배경을 고정 임계값으로 걸렀는데 상품 사진 배경이 밝은 회색이라 배경 69%가
   옷으로 섞였다. 목표가 [51,58,82] → [76,86,115] 로 희석돼 보정이 헛돌았다.
   → 배경색을 네 모서리에서 추정하도록 수정.
2. 흰 배경의 흰 티셔츠는 전경으로 프린트만 7.8% 잡힌다. 그 갈색을 목표로
   삼으면 옷 전체가 갈색이 된다. → 전경 비율이 낮으면 전체를 쓴다.

두 버그 모두 로컬 테스트로 잡히는 종류였으므로  로 분리하고
 를 붙였다(실패 사례를 그대로 테스트로).

**결과.** 색조는 이동했으나(옷 SSIM 1.000 → 0.910) **판정 기준 1을 통과하지 못한다.**
바지가 전보다 어두워졌지만 여전히 밝은 워싱 데님이고, 원본은 무지 다크 네이비
코듀로이다. **문제가 색만이 아니라 질감이다** — 워싱 자국과 흰 줄무늬는 색을
옮겨도 남는다. 색 보정은 색조만 다룰 수 있다.
맨투맨은 해치지 않았다(약간 선명해지는 정도). 안전하지만 충분하지 않다.

### F-2. 합성이 잘 될 조건으로 고른 옷 3벌 — 상의 합격, 하의 기본값 번복

지금까지의 실험으로 잘 되는 조건을 정리하고(단색, 프린트·특수 질감 없음, 흰색이 아닌
중간 톤, 제품 단독 컷) 그 조건으로 무신사에서 반팔·셔츠·바지를 골랐다. 치수표도 같이
옮겼다(`data/size_charts/musinsa_*`). 사진은 `data/samples/set2/` (커밋 제외).

제품 단독 컷 찾기가 의외로 어려웠다. 요즘 상품 대표 사진은 대부분 모델 착용 컷이라,
썸네일 수백 장을 받아 피부색 픽셀 비율과 모서리 배경의 밝기·균일도로 자동으로 걸렀다.

**결과 (샘플 모델 + 본인 사진, 시드 여러 개):**

| 옷 | 결과 |
|---|---|
| 카키 반팔 | 두 인물·시드 3개 모두 색·반팔·목선 정확. **본인 사진 합격** |
| 블루 셔츠 | 칼라·단추·긴팔 깨끗, 시드마다 안정. 색이 원본보다 연함 → 색 보정으로 해결(아래) |
| 올리브 바지 | guidance 5.0에서 **위장무늬처럼 얼룩**, 2.5에서 **깨끗한 단색** |

상의 2벌이 시드를 바꿔도 거의 흔들리지 않았다. 오랑우탄 티가 시드마다 크게 달랐던 것과
대조적이다. **옷을 조건에 맞게 고르면 결과가 안정된다.**

**발견 1 — 하의 guidance 5.0은 틀린 기본값이었다.** 네이비 코듀로이 한 벌이 2.5에서
크림색으로 나와서 올린 값인데, 단색 바지를 망가뜨렸고 코듀로이도 결국 살리지 못했다.
옷 한 벌로 기본값을 정한 실수다. 하의도 2.5로 되돌렸다.

**발견 2 — 색 보정이 후광을 만들었다.** 셔츠 주위에 파란 후광, 바지 주위에 초록 후광.
AutoMasker 마스크는 옷 모양이 아니라 몸 주위를 넉넉히 덮는 영역이라, 그 안에서 모델이
다시 그린 **배경까지** 옷으로 보고 색을 옮긴 탓이다. 원본 인물 사진과 달라진 픽셀만
보정하도록 고쳤고(`color_match.painted_weight`), 받아둔 실제 결과에 로컬로 적용해 후광이
사라지고 셔츠 색이 원본 스틸 블루에 가까워지는 것을 확인했다.

**발견 3 — 반팔 소품.** 사진에서 지운 카드지갑이 손에 들린 채 되살아난 줄 알았는데,
소품과 그림자까지 완전히 지운 사진으로도 샘플 모델의 같은 시드에서 손에 물건이 생겼다.
소품 흔적이 아니라 **샘플 모델의 손 위치(엉덩이 옆)에서 생기는 시드 의존 아티팩트**로 보인다.
본인 사진에서는 나오지 않았다.

**최종 확인 (guidance 2.5 통일, 샘플·본인 × 시드 42/123, 색 보정 없음/있음)**
결과: `data/samples/results/set2_final/_final_summary.jpg`

소매가 없던 팔 부분이 새로 그려진 영역에 들어가 피부까지 옷 색 쪽으로 옮겨진다.
→ 고치려면 산포 배율을 빼고 중앙값만 옮기거나, 피부색 픽셀을 제외해야 한다(미실시).

   팔 자리에 무언가를 그려 넣는다. 지원 범위에서 민소매는 빼거나 마스크를 따로 다뤄야 한다.
4. **테스트 설계 오류 정정.** 초기 벤치마크의 "하의" 케이스 두 개(q08, q10)는 데모에 하의 상품컷이 없어

   형태로 나와 실패인데, 초기 보고에서는 원본 옷을 옆에 두지 않고 "자연스러운 카고 바지"로 적었다.
   원본과 나란히 보지 않으면 틀린 판정이 나온다는 사례다. 두 케이스는 합격률 계산에서 뺐다.

### F-5. 질감이 흐리다 — 줌·DDIM 모두 결 재현은 못 함 (2026-09-13) — ⚠️ 결론은 F-7에서 번복

사용자 지적: "잘 입혀지는데 질감이 흐릿하다". 후보 두 가지를 카톡 사진(따봉 제외 2장) × set2 3벌, 시드 42로 비교했다.
결과: `data/samples/results/texture/_texture_whole.jpg`, `_texture_detail.jpg`, `_texture_1to1.jpg`

### F-8. 변형+GAN 방식(HR-VITON) 비교 — diffusion 유지 근거 (2026-09-13)

|---|---|
| 카톡 정자세 **상반신 크롭** (학습 분포와 가장 비슷) | 형태는 나옴. 글자 프린트가 읽힘. 그러나 **카키 반팔이 검갈색**(원래 입은 검은 티 색이 섞임), 셔츠 보라빛, 소매가 옆으로 늘어난 날개 모양으로 변형, 몸 주위 배경이 뿌옇게 재생성 |

- **결론: diffusion(CatVTON) 유지.** 변형 방식은 빠르지만(약 70배) 실제 사용자 사진(전신, 배경, 원래 옷 색)에서 무너진다. 발표에서 "대안을 실험하고 기각한 근거"로 쓴다.

- 시간은 스텝 수에 거의 비례한다(30→20스텝 약 2/3, T4 fp16 30→50스텝 1.66배). 50스텝이면 P100 fp32 약 4분(추정, 직접 재지 않음).
- 포즈 인식은 onnxruntime을 올려도 CUDA 연결 경고가 남았지만 1회 0.86초라 전체 시간에 영향 없다.
- 5개 결과 모두 이미지 이상(한 색으로 뭉개짐) 없음. 눈으로 보면 fp32·fp16은 서로 같아 보이고 bf16만 음영이 약간 부드럽다. 지표로는 비교하지 않았다.
- **참고 — Gemini 이미지 생성은 같은 종류의 합성을 약 10초에 냈다**(2026-09-14 사용자 시도, 카키 반팔·블루 셔츠).
  사진 전체를 다시 그려서 조명이 자연스럽고 해상도도 높지만, 원본과 다른 곳이 있었다: 카키 반팔의 말린 소매단이 없어지고 박시한 핏이 몸에 맞게 바뀜,
  블루 셔츠 안에 원래 입은 검은 티 대신 흰 티를 만들어 넣음. 속도 차이는 최신 전용 칩·속도용으로 줄인 모델·상시 대기 서버 때문으로 추정(구조 비공개).

**판단:** 속도는 시연용 고성능 GPU로 해결하고 설정은 품질 기준으로 고른다(스텝·guidance는 F-11 그대로 50스텝·2.5).
Kaggle 실험은 **T4 + fp16**으로 한다(50스텝 약 2분, 결과는 fp32와 같음). P100이 걸리면 fp32로 둔다(fp16 이득 없음).
FASHN은 T4·P100에서도 bf16을 고르므로 **dtype을 직접 지정해야 한다.**
bf16을 제대로 지원하는 GPU(L4·A100 등)에서는 bf16이 제일 빠를 수 있으므로, **시연 GPU에서 속도와 결과가 같은지 한 번 확인해야 한다.**

### F-14. 프린트·글자·질감 옷에서도 fp16 = fp32, T4 2장 병렬로 시간 절반 (2026-09-14)

F-13의 미확인 사항(무지 티셔츠 한 벌로만 확인)을 어려운 옷으로 다시 봤다. 앞으로 FASHN 실험을 돌릴 재사용 커널 `kaggle_fashn_t4x2/`를 새로 만들어 돌렸다.

  다만 흰 티의 기장이 원본보다 길게(엉덩이 아래까지) 나왔다 — 핏 충실도는 따로 볼 것.

**판단:** FASHN 실험은 **T4×2 + fp16 + `kaggle_fashn_t4x2/`** 를 표준으로 한다. 50스텝 기준 한 시간에 약 60장.
fp16과 fp32는 품질이 같다고 본다. 단 "같은 시드면 fp32와 픽셀까지 같다"는 보장은 아니므로, 설정 비교는 반드시 같은 dtype끼리 한다.

### F-15. FitDiT — 옷 모양·핏·질감은 FASHN보다 원본에 가깝다, 글자는 FASHN이 낫다 (2026-09-15)

FitDiT(arXiv 2411.10499, CC BY-NC-SA — 비상업 용도라 가능): SD3 기반 트랜스포머 2개(옷용·합성용) + CLIP 인코더 2개, 마스크 영역만 새로 그린다.
커널 `kaggle_fitdit/`(저자 `gradio_sd3.py`의 `FitDiTGenerator`를 그대로 호출). F-14와 **같은 인물·옷 4벌·시드 42·123**, 30스텝(저자 UI 최대)·guidance 2·1152x1536·fp16.
결과: `data/samples/results/fitdit_v2/`(s123 4장, `_E_fitdit_vs_fashn_s123.jpg`), `fitdit_v3/`(s42 오랑우탄·코듀로이), `fitdit_v4/`(s42 맨투맨·셔츠). 비교 그리드 = 원본 옷 | FASHN(F-14 fp16 50스텝 g2.5) | FitDiT.

| 옷 | FASHN | FitDiT |
|---|---|---|
| 블루 셔츠 (2시드) | s123 한쪽 소매 7부·칼라 벌어짐, s42 어깨 덮개(F-11과 같은 흠) | **긴소매·단추·칼라·박시한 핏 원본대로**, 2시드 모두 |
| 오랑우탄 티 (2시드) | 몸에 붙고 기장이 엉덩이 아래까지 길어짐 | **원본처럼 넓고 짧은 오버핏**, 프린트·말풍선 글자 또렷 |
| 코듀로이 바지 (2시드) | 발목 좁은 슬림핏, s42는 **새틴처럼 번들거림** | **통 넓은 일자핏, 골덴 결이 보임** |
| 글자 맨투맨 (2시드) | 몸에 붙는 핏, **글자 또렷** | 원본 래글런·헐렁한 핏, 그러나 **s42 글자 깨짐**("Peimission", "Measurement" 뭉개짐) |

- **FASHN이 옷을 몸에 맞게 "정리"하는 경향이 있고, FitDiT는 원본 옷의 모양을 지킨다.** 사이즈 추천 앱에서는 이게 더 중요하다(박시한 옷이 딱 맞게 보이면 안 됨).
- **자연스러움:** FitDiT는 마스크 밖(얼굴·팔·배경)을 원본 픽셀 그대로 두고, FASHN은 사진 전체를 576x768로 다시 만들어 얼굴·배경까지 살짝 매끈해진다. 사용자 판단도 "FitDiT가 더 자연스럽다".
- 흠: 맨투맨 s42 글자 깨짐. 마스크 방식이라 새 옷이 원래 옷보다 작거나 팔이 몸에 붙으면 흔적·가림이 생길 수 있다(이번 8장에선 안 보임). 마스크는 `_mask__*.png`로 저장.
- **해상도 이득은 아직 못 봤다.** FitDiT는 1152x1536으로 그린 뒤 **입력 인물 사진 크기(768x1024)로 줄여 저장**한다. 고해상도 장점을 보려면 더 큰 원본 사진을 넣어야 한다.

**T4에서 돌리는 조건 (v1~v4 실측)**
- v1: 저자 버전으로 `accelerate`를 0.31로 내리자 Kaggle의 `peft`가 깨져 diffusers import 실패 → Kaggle `accelerate` 유지 + `peft` 제거, `onnxruntime-gpu==1.22`(최신판은 CUDA 13용).
- v2: 가중치만 GPU 12.2GB라 **1152x1536은 T4 16GB에 안 들어간다.** 메모리 부족이 GPU1에선 `OutOfMemoryError`로 와서 offload 전환이 됐지만, GPU0에선 `AcceleratorError`로 와서 못 잡고 4장 실패.
- v3: 처음부터 CPU offload로 워커 2개 → **GPU0 워커가 RAM 부족으로 강제 종료(-9).** offload는 모델 약 12GB를 CPU RAM에 상주시켜 Kaggle RAM(약 30GB)에 둘이 안 들어간다.
- 결론: **T4에서는 offload + 워커 1개**. 장당 약 **2분**(114~129초, 30스텝) — offload인데도 FASHN fp16 50스텝(117초)과 비슷. GPU 2장을 못 쓰므로 Kaggle에서 시간당 약 30장.
  A100(40GB 이상)이면 offload 없이 더 빠를 것(미측정).

**판단:** 원본 옷 충실도(모양·핏·질감)와 자연스러움은 **FitDiT가 FASHN보다 낫다**(8장 중 7장). 글자 프린트만 FASHN이 안정적.
주력 모델 후보를 **FitDiT로 올린다.** 확정 전에 확인할 것: ① 시드·옷을 늘려 글자 깨짐 빈도, ② 스텝 20/30·guidance 조정이 글자에 주는 영향(FASHN은 guidance가 글자에 효과, F-11), ③ 큰 원본 사진으로 고해상도 이득, ④ 가이드대로 찍은 전신 사진에서 하의.

### F-16. FitDiT 정핏 시도 — 마스크를 몸 윤곽으로 자르면 핏은 거의 안 변하고 테두리 얼룩이 생긴다 (2026-09-15)

사용자 요구: 옷 원본 핏(오버핏)이 아니라 **몸에 맞는 핏(정핏)**으로 입혀 보이게.
FitDiT 저자 마스크는 몸과 무관한 큰 직사각형(`_mask__kakao_front_upper__tops.png`)이라, 옷이 퍼질 자리를 줄이면 몸에 맞게 그릴 것이라고 가정했다.
방법: 직사각형 ∩ (부위 인식의 사람 영역을 N px 넓힌 윤곽), N = 8·24(가로 768px 기준). 기장(세로 범위)은 그대로. 커널 `kaggle_fitdit/` `fit_mask()`, F-15 시드 42와 같은 조건 8장.
결과: `data/samples/results/fitdit_fitmask/_F_fitmask_compare.jpg` (원본 옷 | rect(F-15) | body24 | body8 | body8 마스크)

- **핏 변화는 작다.** 맨투맨·오랑우탄 티·바지는 rect와 폭이 거의 같고, body8에서 조금 좁아지는 정도. 모델이 마스크보다 **옷 사진의 모양**을 따라 그린다(저자가 옷 기장·모양을 지키도록 마스크를 느슨하게 학습시킨 설계와 맞는 결과).
- **테두리 얼룩(헤일로)이 생겼다.** 잘린 마스크 경계, 즉 옷이 안 닿는 몸 주변 띠를 배경으로 다시 그리면서 어깨·팔 둘레에 흐린 회색 윤곽이 남는다(body24에서 특히 뚜렷).
- **블루 셔츠 body8은 망가짐:** 어깨 바깥으로 소매가 날개처럼 튀어나옴 — 옷 모양을 좁은 영역에 억지로 넣은 흔적.
- 부수: 맨투맨 글자는 body24·body8에서 "Permission" 정상(rect s42는 "Peimission"). 마스크가 바뀌면 생성 결과 자체가 달라지므로 시드 차이 수준으로 본다.

**판단: 마스크 자르기는 정핏 방법으로 쓰지 않는다.** 코드는 실험 기록으로 남기되 기본값은 `rect`.
FitDiT는 옷 사진의 모양을 따르는 모델이므로 정핏은 입력 쪽에서 유도해야 한다. 다음 후보: **옷 사진의 가로 폭을 줄여서 넣기**(몸판·소매가 좁은 옷으로 보이게). 프린트가 가로로 눌리는 부작용을 같이 확인할 것.

**결정 (2026-09-15): FitDiT는 보류, 주력 모델은 FASHN.**
앱은 옷을 몸에 맞게(정핏) 입혀 보여주는 방향이고, FASHN이 원래 그렇게 입힌다. FitDiT의 자연스러움·원본 핏 충실도는 좋지만 정핏을 만들려면
입력 변형(옷 사진 폭 줄이기)이나 2단계 합성 같은 추가 작업이 필요하다. FASHN 기본값: **fp16 · 50스텝 · guidance 2.5**(F-11·F-14), 실험 커널 `kaggle_fashn_t4x2/`.
FitDiT 커널(`kaggle_fitdit/`)과 결과는 기록으로 남긴다. 다시 볼 조건: FASHN의 흠(글자 휨·셔츠에 없던 디테일, F-11)이 발표에서 문제가 되거나, A100에서 편집 모델 비교를 할 때.

### F-17. 앱에 FASHN 연결 — 실제 GPU에서 합성·사이즈 추천·서버까지 확인 (2026-09-16)

앱의 합성 엔진을 CatVTON에서 FASHN으로 교체했다. 새 파일 `app/fashn_core.py`(엔진), `app/gradio_app.py`(화면) 수정.
CatVTON은 Python 3.9 venv 전용, FASHN은 3.10 이상이라 한 프로세스에서 같이 못 쓴다 → 앱은 기본 파이썬으로 실행한다.
`app/tryon_core.py`(CatVTON)는 벤치마크·과거 실험 재현용으로 남긴다.

- 기본값: **fp16 · 50스텝 · guidance 2.5**(F-11·F-13·F-14). 정밀도는 GPU를 보고 고른다 — compute capability 8 미만(T4·P100)은 fp16, 이상(L4·A100)은 bf16.
- 화면 변경: CatVTON 전용 설정(샘플러·배경 정규화·마스크 보기) 제거, **옷 사진 종류**(상품 사진/착용 사진) 선택 추가, 결과 아래 합성 시간·시드·정밀도 표시.
- 옷 종류 변환: 상의·이너·아우터 → `tops`, 하의 → `bottoms`, 원피스 → `one-pieces`(FASHN은 이너/아우터 구분이 없다).

**검증 (커널 `kaggle_app_check/`, T4)** — 앱 코드를 GitHub에서 받아 실제로 돌렸다.
| 확인 | 결과 |

| `fashn_core.try_on()` | 성공, 576x768, 105초 |
| **F-14 커널 결과와 같은가** | **평균·최대 픽셀 차이 0** — 앱 경로와 실험 경로가 완전히 같은 결과 |

### F. 모델 교체 검토 — IDM-VTON: **평가 후 기각** ✅ 결론

같은 조건(CatVTON 데모 인물 + 오랑우탄 프린트 티)으로 HF 데모에서 직접 돌려 비교했다.
결과 이미지: `data/samples/results/idm_vton/`

| 항목 | 원본 옷 | CatVTON (30스텝) | IDM-VTON |
|---|---|---|---|
| 프린트 | 통통한 매달린 오랑우탄 | 작은 갈색 얼룩 | 형체·색 재현, **세로로 늘어남** |
| 말풍선 | "나마숭떼" | 있으나 글자 뭉개짐 | 있으나 글자가 다름 |
| 소매 | 반팔 | **긴팔로 나옴** | 반팔 |

**IDM-VTON이 더 낫다.** 특히 반팔/긴팔 실루엣을 맞춘 건 CatVTON이 못 한 것이다.
다만 판정 기준 2(프린트 형태)는 IDM-VTON도 완전히는 통과하지 못한다.

**그럼에도 교체하지 않기로 했다.** 이유:

| | CatVTON (현재) | IDM-VTON |
|---|---|---|
| 가중치 | 4GB | **29GB** |
| 환경 | py3.9 / torch 2.1.2 (구축 완료) | py3.10 / torch 2.0.1 (**새로 구축**) |
| 베이스 | SD 1.5 | SDXL — **T4 16GB에 안 들어갈 수 있음** |

HF 데모는 A100(ZeroGPU)에서 돈다. Kaggle T4에서 SDXL 기반이 도는지 불확실하고,
안 되면 29GB를 받아놓고 못 쓴다. 개선 폭(불합격 → 부분 합격)에 비해 비용과
불확실성이 크다. **학부 캡스톤 범위에서는 지금 환경을 안정적으로 유지하고
사이즈 기능·UI를 마무리하는 편이 낫다.**

→ 프린트 재현은 **한계로 명시하고 발표한다.** "무늬 없는 옷과 큰 글자 프린트는
   잘 되고, 사진 프린트는 재현되지 않는다"는 것을 근거 이미지와 함께 보고한다.
   대안을 평가한 뒤 내린 결정이라는 점도 함께 적는다.
